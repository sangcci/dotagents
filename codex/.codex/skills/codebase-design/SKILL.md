**깊은 모듈**을 설계합니다. 작은 인터페이스 뒤에 많은 동작을 두고, 깔끔한 seam에 배치하며, 그 인터페이스를 통해 테스트할 수 있어야 합니다. 코드를 설계하거나 재구성할 때는 이 어휘와 원칙을 씁니다. 목표는 호출자의 leverage, 유지보수자의 locality, 모두의 테스트 용이성입니다.

## 용어

아래 용어를 정확히 이 뜻으로 씁니다. "컴포넌트", "서비스", "API", "경계"로 바꿔 쓰지 않습니다. 용어를 일관되게 쓰는 것이 핵심입니다.

**모듈(Module)**: 인터페이스와 구현을 가진 모든 것입니다. 규모와 무관하게 함수, 클래스, 패키지, 여러 계층에 걸친 슬라이스가 모두 모듈입니다. _피할 말_: 유닛, 컴포넌트, 서비스.

**인터페이스(Interface)**: 호출자가 모듈을 올바르게 쓰려고 알아야 하는 모든 것입니다. 타입 시그니처뿐 아니라 불변식, 호출 순서 제약, 에러 양상, 필요한 설정, 성능 특성을 포함합니다. _피할 말_: API, 시그니처(타입 수준의 표면만 가리켜서 너무 좁습니다).

**구현(Implementation)**: 모듈 안쪽의 코드입니다. **어댑터**와 구별합니다. 구현이 큰 작은 어댑터(Postgres 저장소)도 있고, 구현이 작은 큰 어댑터(인메모리 fake)도 있습니다. seam이 주제일 때는 "어댑터"를, 그 밖에는 "구현"을 씁니다.

**깊이(Depth)**: 인터페이스에서 얻는 leverage입니다. 호출자나 테스트가 배워야 하는 인터페이스 단위당 끌어낼 수 있는 동작의 양입니다. 작은 인터페이스 뒤에 많은 동작이 있으면 **깊고**, 인터페이스가 구현만큼 복잡하면 **얕습니다**.

**Seam**(Michael Feathers): 그 자리를 수정하지 않고도 동작을 바꿀 수 있는 지점입니다. 모듈의 인터페이스가 놓이는 _위치_입니다. seam을 어디에 둘지는 그 뒤에 무엇을 둘지와 별개의 설계 결정입니다. _피할 말_: 경계(DDD의 bounded context와 겹칩니다).

**어댑터(Adapter)**: seam에서 인터페이스를 만족시키는 구체적인 것입니다. 안에 무엇이 들었는지가 아니라 어떤 자리를 채우는지, 곧 역할을 가리킵니다.

**Leverage**: 깊이가 호출자에게 주는 이득입니다. 배워야 하는 인터페이스당 얻는 능력이 커집니다. 구현 하나가 N개의 호출 지점과 M개의 테스트에서 값을 합니다.

**Locality**: 깊이가 유지보수자에게 주는 이득입니다. 변경, 버그, 지식, 검증이 호출자 전체에 퍼지지 않고 한곳에 모입니다. 한 번 고치면 모든 곳이 고쳐집니다.

## 깊은 모듈과 얕은 모듈

**깊은 모듈**은 작은 인터페이스에 많은 구현이 있습니다.

```
┌─────────────────────┐
│   작은 인터페이스   │  ← 메서드가 적고 파라미터가 단순함
├─────────────────────┤
│                     │
│     깊은 구현       │  ← 복잡한 로직이 숨어 있음
│                     │
└─────────────────────┘
```

**얕은 모듈**은 큰 인터페이스에 얇은 구현이 있습니다. 피합니다.

```
┌─────────────────────────────────┐
│          큰 인터페이스          │  ← 메서드가 많고 파라미터가 복잡함
├─────────────────────────────────┤
│  얇은 구현                      │  ← 그냥 넘겨 주기만 함
└─────────────────────────────────┘
```

인터페이스를 설계할 때는 다음을 묻습니다.

- 메서드 수를 줄일 수 있는가?
- 파라미터를 단순하게 만들 수 있는가?
- 복잡성을 더 안쪽에 숨길 수 있는가?

## 원칙

- **깊이는 구현이 아니라 인터페이스의 속성입니다.** 깊은 모듈도 내부는 작고 mock하거나 교체할 수 있는 부품으로 이루어질 수 있습니다. 그 부품들이 인터페이스에 드러나지 않을 뿐입니다. 모듈은 인터페이스에 놓이는 **외부 seam** 말고도, 구현 안쪽에 자기 테스트가 쓰는 **내부 seam**을 가질 수 있습니다.
- **삭제 테스트.** 모듈을 지운다고 상상합니다. 복잡성이 사라지면 그저 통과시키는 모듈이었습니다. 복잡성이 N개의 호출자에게 다시 나타나면 제 몫을 하던 모듈입니다.
- **인터페이스가 곧 테스트 표면입니다.** 호출자와 테스트는 같은 seam을 건넙니다. 인터페이스 _너머_를 테스트하고 싶어진다면 모듈의 모양이 잘못된 것일 가능성이 큽니다.
- **어댑터가 하나면 가상의 seam이고, 둘이면 실제 seam입니다.** 실제로 달라지는 것이 있을 때만 seam을 도입합니다.

## 테스트하기 쉬운 설계

좋은 인터페이스는 테스트를 자연스럽게 만듭니다.

1. **의존성을 만들지 말고 받습니다.**

   ```typescript
   // 테스트하기 쉬움
   function processOrder(order, paymentGateway) {}

   // 테스트하기 어려움
   function processOrder(order) {
     const gateway = new StripeGateway();
   }
   ```

2. **부수 효과를 만들지 말고 결과를 반환합니다.**

   ```typescript
   // 테스트하기 쉬움
   function calculateDiscount(cart): Discount {}

   // 테스트하기 어려움
   function applyDiscount(cart): void {
     cart.total -= discount;
   }
   ```

3. **표면을 작게 유지합니다.** 메서드가 적으면 필요한 테스트가 줄고, 파라미터가 적으면 테스트 준비가 단순해집니다.

## 관계

- **모듈**은 정확히 하나의 **인터페이스**를 가집니다. 호출자와 테스트에 보이는 표면입니다.
- **깊이**는 **모듈**의 속성이며 **인터페이스**를 기준으로 잽니다.
- **Seam**은 **모듈**의 **인터페이스**가 놓이는 곳입니다.
- **어댑터**는 **seam**에 놓여 **인터페이스**를 만족시킵니다.
- **깊이**는 호출자에게 **leverage**를, 유지보수자에게 **locality**를 줍니다.

## 채택하지 않은 틀

- **깊이를 구현 줄 수 대 인터페이스 줄 수의 비율로 보는 관점**(Ousterhout): 구현을 부풀리는 쪽에 보상을 줍니다. 여기서는 깊이를 leverage로 봅니다.
- **"인터페이스"를 TypeScript `interface` 키워드나 클래스의 public 메서드로 보는 관점**: 너무 좁습니다. 여기서 인터페이스는 호출자가 알아야 하는 모든 사실을 포함합니다.
- **"경계"**: DDD의 bounded context와 겹칩니다. **seam**이나 **인터페이스**라고 말합니다.
