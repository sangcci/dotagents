# 모듈 깊게 만들기

얕은 모듈 묶음을 의존성에 맞춰 안전하게 깊게 만드는 방법입니다. [SKILL.md](SKILL.md)의 어휘인 **모듈**, **인터페이스**, **seam**, **어댑터**를 전제로 합니다.

## 의존성 분류

깊게 만들 후보를 평가할 때 의존성을 분류합니다. 분류에 따라 깊어진 모듈을 seam 너머에서 테스트하는 방법이 정해집니다.

### 1. 프로세스 내부

순수 계산, 인메모리 상태처럼 I/O가 없는 경우입니다. 언제나 깊게 만들 수 있습니다. 모듈을 합치고 새 인터페이스를 직접 통해 테스트합니다. 어댑터는 필요 없습니다.

### 2. 로컬에서 대체 가능

로컬 테스트용 대체물이 있는 의존성입니다(Postgres 대신 PGLite, 인메모리 파일시스템). 대체물이 있으면 깊게 만들 수 있습니다. 깊어진 모듈은 테스트 스위트에서 그 대체물을 띄워 테스트합니다. seam은 내부에 있고, 모듈의 외부 인터페이스에는 포트를 두지 않습니다.

### 3. 원격이지만 직접 소유(포트와 어댑터)

네트워크 너머에 있는 자체 서비스입니다(마이크로서비스, 내부 API). seam에 **포트**(인터페이스)를 정의합니다. 깊은 모듈이 로직을 소유하고, 전송 계층은 **어댑터**로 주입합니다. 테스트는 인메모리 어댑터를, 운영은 HTTP, gRPC, 큐 어댑터를 씁니다.

권장 형태: "seam에 포트를 정의하고, 운영용 HTTP 어댑터와 테스트용 인메모리 어댑터를 구현해서, 네트워크를 가로질러 배포되더라도 로직은 깊은 모듈 하나에 있게 한다."

### 4. 진짜 외부(Mock)

통제할 수 없는 서드파티 서비스입니다(Stripe, Twilio 등). 깊어진 모듈이 외부 의존성을 주입받는 포트로 받고, 테스트에서는 mock 어댑터를 제공합니다.

## Seam 규율

- **어댑터가 하나면 가상의 seam이고, 둘이면 실제 seam입니다.** 어댑터가 최소 둘(보통 운영과 테스트) 정당화될 때만 포트를 둡니다. 어댑터가 하나뿐인 seam은 간접 참조일 뿐입니다.
- **내부 seam과 외부 seam.** 깊은 모듈은 외부 인터페이스의 seam 말고도, 구현 안쪽에 자기 테스트가 쓰는 내부 seam을 가질 수 있습니다. 테스트가 쓴다는 이유로 내부 seam을 인터페이스에 노출하지 않습니다.

## 테스트 전략: 쌓지 말고 교체

- 모듈을 깊게 만든 뒤 그 인터페이스에서 테스트를 쓰고 나면, 얕은 모듈 시절의 단위 테스트는 낭비가 됩니다. 삭제합니다.
- 새 테스트는 깊어진 모듈의 인터페이스에서 씁니다. **인터페이스가 곧 테스트 표면**입니다.
- 테스트는 내부 상태가 아니라 인터페이스를 통해 관찰되는 결과를 검증합니다.
- 테스트는 내부 리팩터링에도 살아남아야 합니다. 구현이 아니라 동작을 설명하기 때문입니다. 구현이 바뀔 때 테스트도 바꿔야 한다면 인터페이스 너머를 테스트하고 있는 것입니다.
