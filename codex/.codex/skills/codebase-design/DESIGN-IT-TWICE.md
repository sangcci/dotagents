# 두 번 설계하기

선택한 deepening 후보의 대안 인터페이스를 탐색하고 싶을 때 이 병렬 서브에이전트 패턴을 씁니다. Ousterhout의 "Design It Twice"에 바탕을 둡니다. 처음 떠올린 안이 최선일 가능성은 낮습니다.

[SKILL.md](SKILL.md)의 어휘인 **모듈**, **인터페이스**, **seam**, **어댑터**, **leverage**를 씁니다.

## 절차

### 1. 문제 공간 정리

서브에이전트를 띄우기 전에, 선택한 후보의 문제 공간을 사용자에게 설명하는 글을 씁니다.

- 새 인터페이스가 만족해야 하는 제약
- 의존하게 될 대상과 그 분류([DEEPENING.md](DEEPENING.md) 참고)
- 제약을 구체적으로 보여 주는 대략적인 코드 스케치. 제안이 아니라 제약을 눈에 보이게 하는 용도입니다.

이 글을 사용자에게 보여 준 뒤 곧바로 2단계로 넘어갑니다. 서브에이전트가 병렬로 일하는 동안 사용자는 읽고 생각합니다.

### 2. 서브에이전트 실행

새 컨텍스트를 가진 서브에이전트 3개 이상을 병렬로 띄웁니다. 각자 깊어진 모듈의 인터페이스를 **근본적으로 다르게** 설계해야 합니다.

서브에이전트마다 별도의 기술 브리프(파일 경로, 결합 상세, [DEEPENING.md](DEEPENING.md)의 의존성 분류, seam 뒤에 놓일 것)를 줍니다. 브리프는 1단계에서 사용자에게 보여 준 문제 공간 설명과 독립입니다. 에이전트마다 다른 설계 제약을 줍니다.

- 에이전트 1: "인터페이스를 최소화한다. 진입점은 많아야 1~3개. 진입점당 leverage를 최대화한다."
- 에이전트 2: "유연성을 최대화한다. 많은 사용 사례와 확장을 지원한다."
- 에이전트 3: "가장 흔한 호출자에 최적화한다. 기본 사례를 사소하게 만든다."
- 에이전트 4(해당할 때): "seam을 가로지르는 의존성에 대해 포트와 어댑터를 중심으로 설계한다."

각 서브에이전트가 아키텍처 어휘와 프로젝트의 도메인 용어를 일관되게 쓰도록, 브리프에 [SKILL.md](SKILL.md)의 어휘와 프로젝트 용어집이 있으면 그 용어를 함께 넣습니다.

각 서브에이전트는 다음을 출력합니다.

1. 인터페이스(타입, 메서드, 파라미터, 불변식, 호출 순서, 에러 양상)
2. 호출자가 쓰는 모습을 보여 주는 사용 예
3. seam 뒤에 구현이 숨기는 것
4. 의존성 전략과 어댑터([DEEPENING.md](DEEPENING.md) 참고)
5. 트레이드오프: leverage가 높은 곳과 얇은 곳

### 3. 제시와 비교

사용자가 하나씩 소화할 수 있도록 설계를 차례로 보여 준 뒤 글로 비교합니다. **깊이**(인터페이스의 leverage), **locality**(변경이 모이는 곳), **seam 위치**로 대비합니다.

비교한 뒤 가장 강하다고 보는 설계와 이유를 직접 제시합니다. 서로 다른 설계의 요소가 잘 맞으면 혼합안을 제안합니다. 선택지 목록이 아니라 분명한 의견을 냅니다.
