# 문체와 주장 범위

## 담담하고 구체적으로 쓰기

본인이 한 행동과 판단은 직접 말한다. 성과에 대한 평가는 독자가 근거를 보고 할 수 있게 한다. 측정값이 없어도 확인한 동작과 판단이 구체적이면 사용할 수 있다.

- `책임 분리`, `구조 개선`, `기준 정립`은 제목으로 쓸 수 있다. 본문에서는 무엇을 나누고 어떤 기준을 정했는지 밝힌다.
- `분리했습니다` 뒤에는 어떤 책임을 어디에 뒀는지, `개선했습니다` 뒤에는 무엇이 달라졌는지 설명한다.
- `생각했습니다`는 판단에, `느꼈습니다`는 체감한 변화에 쓴다. 실행으로 확인한 사실에 불확실한 어미를 반복하지 않는다.
- `부담이 줄었다고 느꼈습니다`를 관찰 근거 없이 `생산성을 높였습니다`로 바꾸지 않는다. 체감만 남고 행동이 드러나지 않으면 확인된 작업을 중심으로 다시 쓴다.
- `열정적인`, `끊임없이`, `성공적으로`처럼 행동을 설명하지 않는 수식어는 줄인다.
- 실제로 한 질문은 맥락을 보여줄 때 사용할 수 있다. 하지 않은 말이나 반응을 직접 인용처럼 만들지 않는다.
- 굵은 글씨는 핵심 판단이나 확인된 결과에만 선택적으로 사용한다. 가운데점 대신 쉼표, 접속사나 줄바꿈을 쓴다.

## 동사에 맞는 근거

아래 항목은 반드시 거쳐야 하는 단계가 아니라 서로 다른 사실이다. 확보한 근거에 맞는 동사를 선택한다.

| 표현 | 필요한 근거와 주의점 |
| --- | --- |
| 제안했습니다 | 본인이 제시한 선택지나 변경안이 있다. 팀의 채택이나 구현을 뜻하지 않는다. |
| 비교했습니다 | 비교 대상과 기준, 결과가 있다. 후보 이름을 나열한 것과 구분한다. |
| 설계했습니다 | 처리 규칙과 경계 등 본인이 결정한 범위가 있다. 구현 완료로 확대하지 않는다. |
| 구현했습니다 | 해당 동작을 코드로 만들었다. 실행 성공과 운영 효과는 별도로 확인한다. |
| 테스트를 작성했습니다 | 검증 코드가 있다. 실행 기록 없이 `테스트에서 확인했습니다`로 바꾸지 않는다. |
| 테스트에서 확인했습니다 | 실행 결과와 검사한 조건을 확인했다. 검사하지 않은 경로로 일반화하지 않는다. |
| 배포했습니다 | 반영한 환경과 버전 등 배포 근거가 있다. 실제 사용자 이용과 효과를 뜻하지 않는다. |
| 운영에서 확인했습니다 | 실제 사용 중 관찰한 로그, 지표나 사례가 있다. 의도한 동작과 구분한다. |
| 주도했습니다 | 본인이 결정과 조율을 이끈 범위가 있다. 직책이나 커밋 수만으로 판단하지 않는다. |

팀 결과와 개인 기여를 구분한다. AI와 함께 작업했다면 본인이 정한 기준, 검토와 수정 범위를 밝힌다. 직접 코드를 모두 작성한 것처럼 바꾸거나 근거 없이 오류 감소를 주장하지 않는다.

## 주의할 표현

다음은 금지어 목록이 아니다. 단어를 기계적으로 삭제하거나 동의어로 바꾸지 말고, 그 단어가 주장하는 범위를 근거와 대조한다. 조건이 분명하고 근거가 충분하면 사용할 수 있다.

| 표현 | 확인할 내용 | 작성 기준 |
| --- | --- | --- |
| 보장, 온전히 방지, 제거 | 관련된 모든 경로와 실제 조건을 확인했는가? | 검증한 경로, 조건과 결과를 명시한다. 일부 테스트로 전체 시스템의 정합성을 보장했다고 쓰지 않는다. |
| 해결 | 처음 제시한 문제가 실제로 해소됐는가? | 해결한 문제를 구체적으로 밝힌다. 구현 완료나 부분 완화를 전체 해결로 확대하지 않는다. |
| 최적, 최적화 | 무엇을 기준으로 어떤 방법을 비교했는가? | 비교한 기준과 범위를 밝히고, 응답 시간이나 비용처럼 개선한 대상을 직접 적는다. 최고라는 근거가 없으면 `최적` 대신 이 내용을 쓴다. |
| 안정성, 신뢰성 향상 | 어떤 실패를 어떻게 처리하게 됐는가? | 실패 조건과 바뀐 동작을 적는다. 타임아웃, 오류 구분, 중복 처리가 예다. |
| 확장성 확보 | 어떤 확장과 부하를 검토했는가? | 실제 대응한 변화나 검증 범위를 밝힌다. 설계상 대응 가능성과 실제 검증을 구분하며, 모듈 분리만으로 확장성을 주장하지 않는다. |
| 생산성, 효율 향상 | 시간이나 작업 과정이 어떻게 달라졌는가? | 없어진 반복 작업이나 줄어든 절차를 적는다. 도구 도입을 효과로 간주하지 않는다. |
| 가독성, 유지보수성 향상 | 어떤 변경을 어디에서 처리하기 쉬워졌는가? | 분리한 책임과 변경 전후 차이를 보여준다. 테스트 통과를 가독성의 증거로 쓰지 않는다. |
| 자동화 | 무엇이 어떤 계기로 실행되며 수동 작업은 어디에 남는가? | 실제 자동 처리 범위를 적는다. 스크립트 작성만으로 전체 업무 자동화를 주장하지 않는다. |
| 구축, 설계, 주도 | 본인이 결정하고 구현한 범위는 어디까지인가? | 담당 범위와 직접 한 행동을 밝힌다. 팀 전체의 시스템을 개인 성과로 확장하지 않는다. |
| 대폭, 획기적, 성공적, 완벽, 무중단 | 이 평가를 뒷받침할 비교나 관찰이 있는가? | 수식어를 빼고 결과를 그대로 적는다. 무중단처럼 기술적 의미가 있는 표현은 조건과 근거가 있을 때 쓴다. |

`보장했습니다`를 `보장하도록 구현했습니다`로 바꿔도 범위가 넓으면 문제는 남는다. 목표, 구현한 장치와 실제 확인한 결과를 구분한다. 모든 문장에 한계 설명을 덧붙이지 말고, 독자의 결론이 달라지는 조건을 남긴다.

## 검증 결과를 표현하는 기준

- 성능 수치는 API와 SQL, 평균과 p95, 처리량과 동시 요청 수를 구분한다. 데이터 분포, 부하와 캐시 상태 등 해석에 필요한 조건을 남긴다.
- 전후 조건이 다르면 개선율을 바로 계산하지 않는다. 서로 다른 실험의 수치는 조건을 표시해 구분한다.
- 두 동시 저장 요청의 결과를 확인했다면 저장과 취소의 경합까지 검증했다고 쓰지 않는다.
- PoC 표본의 정확도와 비용은 해당 실험의 결과로 쓴다. 일부 필드의 일치를 전체 정확도로, 추정 비용을 실제 비용 절감으로 바꾸지 않는다.
- 이벤트 리스너나 DLT를 추가했다는 사실만으로 전달 보장, 재시도와 복구를 주장하지 않는다.
- 실제 장애를 겪지 않았다면 장애 재현 실험이라고 쓴다. 가정한 사용자 규모를 실제 트래픽으로 표현하지 않는다.

## 문장 수정 예시

아래는 가상 예시다. 수정 문장은 해당 구현이나 실행 근거가 있을 때만 사용할 수 있다. 자료가 없으면 확인하거나 주장 자체를 줄인다.

| 모호하거나 범위가 넓은 문장 | 근거에 맞춘 문장 |
| --- | --- |
| 동시성 문제를 해결해 정합성을 보장했습니다. | 두 요청이 동시에 최초 저장을 수행해도 오류 없이 저장 관계가 한 행만 남는지 통합 테스트에서 확인했습니다. |
| 책임을 분리해 유지보수성을 개선했습니다. | 환율 API 호출과 응답 처리를 연동 코드에 두고, 환율 적용일을 결정하는 업무 코드와 구분했습니다. |
| 문서 자동화로 생산성을 크게 높였습니다. | 정책서 PR이 머지되면 Confluence에 변경 내용을 반영하도록 구성했습니다. |
| 외부 연동의 안정성을 확보했습니다. | 환율 API의 HTTP 오류를 정상적인 빈 결과와 구분해 호출자에게 전달하도록 구현했습니다. |

자료가 테스트 작성만 입증한다면 첫 예시는 `두 동시 최초 저장 요청 후 저장 관계가 한 행인지 검사하는 통합 테스트를 작성했습니다`까지 쓴다. 결과를 단정하지 않으면서도 실제 작업을 구체적으로 전달한다.
