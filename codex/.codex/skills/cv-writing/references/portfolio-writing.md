# 포트폴리오 작성 가이드

이력서의 핵심 주장을 관찰 근거, 선택 과정과 검증 결과로 설명한다. 이력서를 길게 풀어 쓰거나 기술 매뉴얼을 재현하지 않는다. 문체와 성과 표현은 [문체와 주장 범위](wording-and-evidence.md)를 따른다.

## 사례 선택과 역할

- 가장 잘 설명하고 근거를 제시할 수 있는 경험부터 배치한다. 진행 중인 기능을 분량 확보를 위해 완료 사례로 바꾸지 않는다.
- 프로젝트 전체의 구성과 본인이 다룬 범위를 구분한다. 공동 작업은 본인의 설계, 구현과 검토 범위를 밝힌다.
- 실제 운영 개선, 기존 코드의 변경, 가정한 장애 실험과 PoC를 구분한다.
- 지원 회사에 맞춰 사례를 고를 때는 확인한 공고와 서비스 특성만 연결한다.

## 문제에서 검증까지 연결하기

아래 질문 중 해당 사례의 판단에 필요한 내용을 고른다. 모든 제목과 항목을 고정 양식으로 만들지 않는다.

| 관점 | 독자가 확인할 내용 |
| --- | --- |
| 문제와 기준 | 관찰한 현상, 영향과 정상 동작의 기준. 실제 요구와 실험 가정을 구분한다. |
| 원인 | 로그, 실행 계획이나 코드 흐름에서 무엇을 확인했고 원인을 어떻게 좁혔는가? |
| 전체 변경 경로 | 생성, 수정, 취소와 삭제 등 관련 경로에서 어떤 불변식을 지켜야 하는가? |
| 선택 | 실제 비교한 대안과 당시 일정, 인력, 비용, 기존 구조를 고려한 판단 |
| 구현 | 데이터 흐름, 트랜잭션 경계와 외부 부수 효과의 순서. 무엇을 어디에 바꿨는가? |
| 실패와 복구 | 중간 실패 이후 남는 상태, 반복 요청과 재처리의 동작. 실제 확인한 범위는 어디까지인가? |
| 검증 | 확인할 주장, 실행 환경, 데이터 조건과 결과. 어떤 잘못된 구현을 구분할 수 있는가? |
| 결과와 한계 | 원래 문제의 해소 여부, 미검증 조건과 선택을 다시 검토할 조건 |

기술을 먼저 골랐다면 그 이력을 보존한다. 이후 필요성을 검토하거나 재실험한 과정을 당시 판단인 것처럼 바꾸지 않는다. 실제로 비교하지 않은 대안은 당시 검토했다고 쓰지 않는다.

## 기술적 구체성 고르기

- 구조 분리는 클래스 목록보다 책임과 변경 경계의 차이를 보여준다.
- 동시성은 잠금 이름보다 보호할 규칙, 경합 경로와 최종 데이터 상태를 설명한다.
- 외부 연동은 호출 성공뿐 아니라 업무상 빈 결과, 입력 오류와 공급자 실패의 구분을 보여준다.
- 성능은 측정 조건과 원인 분석을 남긴다. 쿼리 수 감소가 사용자 지연 감소로 이어졌는지는 별도로 확인한다.
- AI와 OCR 실험은 표본과 정답 검수 방식, 필드별 결과와 추정 비용을 구분한다. 모델을 사용했다는 사실을 평가 결과 대신 쓰지 않는다.
- 운영 설명은 수집한 지표와 로그가 어떤 판단에 쓰였는지 보여준다. 설치한 도구 목록만으로 장애 대응 경험을 주장하지 않는다.

이 내용은 문서 작성에 필요한 근거 선택 기준이다. 사용자의 요청 없이 코드 개선이나 새 검증 작업을 시작하는 지시가 아니다.

## 근거 제시

핵심 주장을 뒷받침하는 코드, 테스트, 실험 기록과 결정 기록을 연결한다. 캡처에는 무엇을 관찰해야 하는지 설명한다. 링크가 본문 설명을 대신하게 두지 않는다.

아키텍처 그림에는 실제 실행 단위와 통신 경로를 구분하고 본인의 담당 범위를 표시한다. 제안 구조는 현재 배포 구조와 구분한다. 모든 도구를 넣기보다 해당 사례의 판단에 필요한 구성요소를 고른다.

미확인 사항은 검토용 초안에서 표시한다. 제출 문서는 그 사실에 기대는 주장을 제외하거나 확인된 범위로 고친다. 모든 사례에 형식적인 한계와 향후 과제를 붙이지 않는다.

## 이력서와의 일관성

동일한 실험의 수치와 기간, 역할은 일치시킨다. 다른 실험은 조건을 표시해 구분한다. 설명을 길게 쓰는 과정에서 PoC를 서비스 적용으로, 단일 환경 실험을 운영 전체의 보장으로 확대하지 않는다.

소제목마다 하나의 판단을 다루고, 상세 코드와 로그는 필요한 부분만 고른다. 문장을 짧게 줄이면서 원인과 조치의 관계를 끊지 않는다. 페이지 수나 글자 수를 일률적으로 정하지 않고 사용자가 지정한 형식과 독자의 탐색 흐름에 맞춘다.
