# 이력서 작성 가이드

이력서와 경력기술서는 문제와 본인의 판단, 작업과 결과를 짧은 시간에 파악할 수 있게 쓴다. 기존 문서와 사용자의 수정은 보존한다. 프로젝트 수나 모든 사례의 문장 수를 고정하지 않는다.

문체와 검증 표현은 [문체와 주장 범위](wording-and-evidence.md)를 따른다.

## 프로젝트 첫머리

기간과 필요한 팀 구성, 주요 기술은 짧은 메타 정보로 제공한다. 서비스의 목적, 참여 시점과 역할은 세 줄 안팎으로 설명한다.

- 서비스가 누구의 어떤 문제를 해결하는지 밝힌다.
- 기획 초기 참여, 운영 중 합류와 종료 후 개인 개선을 구분한다.
- 직책과 직접 맡은 영역을 구분한다. 상세 활동은 아래 경험 항목에 둔다.
- 팀 개발과 개인 개선 기간을 구분한다. 첫 커밋 날짜를 실제 합류일로 단정하지 않는다.

## 경험 항목 구성

아래는 기본 구성이다. 짧은 사례는 통합하고, 긴 사례는 상세 자료로 연결한다. 분량을 맞추려고 없는 배경과 결과를 추가하지 않는다.

### 짧은 소제목

수행한 일이나 해결한 문제를 밝힌다. 기술 이름과 개선율만 제목에 두거나 배경 전체를 압축하지 않는다.

- 인증 흐름 리팩토링
- 정책서와 문서 관리 체계 정비
- 즐겨찾기 반복 요청과 동시 저장 처리

### 상황과 접근

독자가 개선 필요성을 판단할 수 있는 문제와 제약을 먼저 쓴다. 이어서 접근 방법과 선택 근거를 연결한다. 보통 두세 문장으로 쓰되 간단한 사례는 한 문장으로 줄인다.

추상적인 불편 대신 무엇을 이해하기 어려웠는지, 어떤 조회가 어떤 조건에서 느렸는지 밝힌다. 학습 목적의 실험이라면 그 사실을 유지한다.

### 직접 한 일과 검증

핵심 작업을 목록으로 고른다. 같은 목적의 테스트는 묶고, 어떤 조건에서 무엇을 검사했는지 적는다. 공통 설정과 부수 작업을 빠짐없이 나열하지 않는다.

목록은 `호출 순서 분석`, `통합 테스트 작성`처럼 끝낼 수 있다. 관계가 복잡하면 `두 요청이 동시에 처음 저장해도 한 행만 남는지 검사하는 테스트 작성`처럼 풀어 쓴다. 첫 문단에 쓴 구현 설명을 목록에서 그대로 반복하지 않는다.

### 결과

처음의 문제나 목적에 답한다. `분리했습니다`, `정리했습니다`로 작업을 되풀이하지 말고, 달라진 동작이나 확인된 상태를 쓴다. 앞부분에서 결과까지 충분히 전달했다면 별도 결과 문단을 강제하지 않는다.

- 구조 변경은 업무 흐름을 어디에서 읽고, 변경할 책임이 어디에 놓였는지 보여준다.
- 문서 정비는 정책 원본과 변경 이유를 어디에서 함께 확인하게 됐는지 설명한다.
- 기능 구현은 구현한 규칙과 실행으로 확인한 결과를 구분한다.
- 성능 개선은 같은 조건의 지표를 비교하고 원래 문제가 얼마나 해소됐는지 밝힌다.

## 압축할 때 남길 내용

문제의 필요성, 본인의 판단과 기여, 결과를 해석하는 데 필요한 조건을 남긴다. 상세 실험 절차와 전체 대안 비교는 포트폴리오에 둔다. 이력서만 읽어도 핵심 주장을 오해하지 않게 한다.

삭제 순서는 반복 설명, 일반적인 기능 목록, 주변 설정과 부수 구현을 우선한다. 핵심 선택 이유를 지우고 기술 이름과 수치만 남기지 않는다. 측정 수치가 없다는 이유로 근거 있는 정책 판단과 협업 경험을 제외하지 않는다.

## 기능 구현 예시

다음은 가상 형식 예시다. 테스트 실행 기록이 없는 상황을 전제로 하며 사용자의 실제 경험을 증명하지 않는다.

### 즐겨찾기 반복 요청과 동시 저장 처리

반복 저장 요청으로 최신 저장순 목록의 순서가 바뀌지 않도록, 이미 저장된 관계의 변경 시각을 유지하도록 구현했습니다.

- 사용자와 장소 조합에 유일 제약과 UPSERT 적용
- 반복 요청의 상태와 변경 시각을 검사하는 MySQL 통합 테스트 작성
- 두 동시 최초 저장 요청 후 오류 없이 한 행만 남는지 검사하는 테스트 작성

실행 결과가 확인되지 않은 상태에서 중복 저장 문제가 해결됐다고 덧붙이지 않는다. 검토용 초안에는 실행 결과 확인을 남기고, 제출 문서에는 확인된 작업만 담는다.

## 성능 개선 사례

관찰한 지연이나 비용, 분석한 원인, 선택한 조치와 검증 결과를 연결한다. API 응답 시간인지 SQL 실행 시간인지 명시한다. 상세 환경은 연결된 자료로 옮길 수 있지만 비교에 중요한 조건은 남긴다.

개선 필요성이나 측정 근거가 없으면 수치 중심의 성능 성과로 만들지 않는다. 확인한 구현이나 학습 실험의 범위로 설명한다.

## 최종 점검

- 제목과 첫 문단에서 문제와 본인 역할이 보이는가?
- 본문, 목록과 결과가 같은 구현을 반복하지 않는가?
- 결과가 처음 제시한 문제에 답하는가?
- 핵심 판단과 검증 조건을 지우고 성과만 강조하지 않았는가?
- 문서 간 수치, 기간과 역할을 대조했는가?
- 상세 자료로 옮긴 내용을 확인할 경로가 있는가?
