name: diff-review
description: 고정된 기준점(커밋, 브랜치, 태그, merge-base) 이후의 변경을 두 축으로 리뷰한다. Standards는 repo에 문서화된 코딩 규약을 따르는지, Spec은 원래 요구사항대로 구현했는지 본다. 두 리뷰를 병렬 서브에이전트로 돌려 나란히 보고한다. 브랜치, PR, 작업 중인 변경을 리뷰하거나 "X 이후 변경 리뷰해 줘"라고 요청할 때 사용한다.
---

`HEAD`와 사용자가 지정한 기준점 사이의 diff를 두 축으로 리뷰합니다.

- **Standards**: 코드가 이 repo에 문서화된 코딩 규약을 따르는가?
- **Spec**: 코드가 원래의 요구사항(이슈, 명세)을 충실히 구현하는가?

두 축은 서로의 컨텍스트를 오염시키지 않도록 **병렬 서브에이전트**로 실행하고, 이 스킬이 결과를 모아 보고합니다. 서브에이전트는 모두 새 컨텍스트로 시작합니다. 구현 에이전트는 탐색과 디버깅으로 컨텍스트 압박이 가장 크고, 리뷰 에이전트는 diff만 받아 압박이 가장 작습니다. 그래서 규약을 점검하는 일은 구현 쪽이 아니라 리뷰 쪽에 맡깁니다.

## 절차

### 1. 기준점 고정

사용자가 말한 것이 기준점입니다(커밋 SHA, 브랜치 이름, 태그, `main`, `HEAD~5` 등). 지정하지 않았다면 묻습니다.

diff 명령은 한 번만 정해 둡니다. `git diff <기준점>...HEAD`(점 세 개, 기준점이 아니라 merge-base와 비교)를 쓰고, 커밋 목록은 `git log <기준점>..HEAD --oneline`으로 얻습니다.

다음 단계로 가기 전에 기준점이 해석되는지(`git rev-parse <기준점>`)와 diff가 비어 있지 않은지 확인합니다. 잘못된 ref나 빈 diff는 병렬 서브에이전트 안이 아니라 여기서 실패해야 합니다.

### 2. Spec 출처 찾기

원래의 명세를 다음 순서로 찾습니다.

1. 커밋 메시지의 이슈 참조(`#123`, `Closes #45`, GitLab `!67` 등). `gh` 같은 CLI로 가져올 수 있으면 가져옵니다.
2. 사용자가 인자로 준 경로.
3. 브랜치 이름이나 기능에 맞는 `docs/`, `specs/` 아래의 명세 파일.
4. 아무것도 없으면 명세가 어디 있는지 묻습니다. 없다고 답하면 **Spec** 서브에이전트는 건너뛰고 "명세 없음"으로 보고합니다.

### 3. Standards 출처 찾기

repo에서 코드 작성 방식을 문서화한 파일을 모두 찾습니다. `CODING_STANDARDS.md`나 `CONTRIBUTING.md`가 있으면 반드시 목록에 넣고, 에이전트 지침 파일(`AGENTS.md`, `CLAUDE.md`)이 가리키는 규약 문서도 포함합니다.

repo가 문서화한 것과 별개로, Standards 축에는 항상 아래 **냄새 기준선**이 적용됩니다. Fowler의 코드 냄새(_Refactoring_ 3장) 중 고정된 묶음이며, repo가 아무것도 문서화하지 않았어도 적용됩니다. 두 규칙이 붙습니다.

- **repo가 우선합니다.** 문서화된 repo 규약이 항상 이깁니다. 기준선이 지적할 만한 것을 규약이 허용하면 그 냄새는 보고하지 않습니다.
- **항상 판단입니다.** 각 냄새는 "Feature Envy 가능성"처럼 라벨을 붙인 휴리스틱이며 확정된 위반이 아닙니다. 다른 규약과 마찬가지로 도구가 이미 강제하는 것은 건너뜁니다.

각 냄새는 _무엇인지_ → _어떻게 고치는지_ 순서로 적었고, diff에 대조해 봅니다.

- **Mysterious Name**: 함수, 변수, 타입의 이름이 하는 일이나 담긴 것을 드러내지 않습니다. → 이름을 바꿉니다. 정직한 이름이 떠오르지 않으면 설계가 흐릿한 것입니다.
- **Duplicated Code**: 같은 로직 모양이 변경 안의 여러 hunk나 파일에 나타납니다. → 공통 모양을 추출해 양쪽에서 호출합니다.
- **Feature Envy**: 메서드가 자기 데이터보다 다른 객체의 데이터를 더 많이 만집니다. → 부러워하는 데이터가 있는 쪽으로 메서드를 옮깁니다.
- **Data Clumps**: 같은 필드나 파라미터 몇 개가 늘 같이 다닙니다(태어나고 싶은 타입). → 하나의 타입으로 묶어 그것을 넘깁니다.
- **Primitive Obsession**: 자기 타입을 가질 만한 도메인 개념을 원시 타입이나 문자열이 대신합니다. → 그 개념에 작은 타입을 줍니다.
- **Repeated Switches**: 같은 타입에 대한 같은 `switch`나 `if` 연쇄가 변경 곳곳에 반복됩니다. → 다형성이나 두 곳이 공유하는 맵 하나로 바꿉니다.
- **Shotgun Surgery**: 논리적 변경 하나가 여러 파일의 산발적인 수정을 강요합니다. → 함께 바뀌는 것을 한 모듈로 모읍니다.
- **Divergent Change**: 파일이나 모듈 하나가 서로 무관한 여러 이유로 수정됩니다. → 모듈마다 하나의 이유로만 바뀌도록 나눕니다.
- **Speculative Generality**: 명세에 없는 필요를 위해 추상화, 파라미터, 훅을 추가했습니다. → 지웁니다. 실제 필요가 나타날 때까지 인라인으로 되돌립니다.
- **Message Chains**: 호출자가 의존하면 안 되는 `a.b().c().d()` 식 긴 탐색입니다. → 첫 객체의 메서드 하나 뒤로 탐색을 숨깁니다.
- **Middle Man**: 대부분 다른 곳으로 위임하기만 하는 클래스나 함수입니다. → 없애고 실제 대상을 직접 호출합니다.
- **Refused Bequest**: 상속받은 것 대부분을 무시하거나 재정의하는 하위 클래스나 구현체입니다. → 상속을 버리고 합성을 씁니다.

### 4. 서브에이전트 병렬 실행

두 서브에이전트 호출을 함께, 포그라운드로 내고 돌아온 보고를 모읍니다.

**Standards 서브에이전트 프롬프트**에 넣을 것:

- 전체 diff 명령과 커밋 목록.
- 3단계에서 찾은 규약 파일 목록, **그리고 3단계의 냄새 기준선 전문**(서브에이전트는 다른 경로로 접근할 수 없습니다).
- 지시: "파일이나 hunk별로 (a) diff가 문서화된 규약을 위반하는 모든 곳을 규약 파일과 규칙을 인용해 보고하고, (b) 보이는 기준선 냄새의 이름과 해당 hunk를 인용해 보고한다. 확정 위반과 판단 사항을 구분한다. 문서화된 규약 위반은 확정일 수 있지만 기준선 냄새는 항상 판단이며, 문서화된 repo 규약이 기준선보다 우선한다. 도구가 강제하는 것은 건너뛴다. 400단어 이내."

**Spec 서브에이전트 프롬프트**에 넣을 것:

- diff 명령과 커밋 목록.
- 명세의 경로나 가져온 내용.
- 지시: "(a) 명세가 요구했지만 빠졌거나 일부만 구현된 것, (b) 요구하지 않았는데 diff에 있는 동작(범위 초과), (c) 구현된 것처럼 보이지만 구현이 틀려 보이는 요구사항을 보고한다. 각 항목마다 명세의 해당 줄을 인용한다. 400단어 이내."

명세가 없으면 Spec 서브에이전트를 건너뛰고 최종 보고에 그 사실을 적습니다.

### 5. 취합

두 보고를 `## Standards`와 `## Spec` 제목 아래에 원문 그대로 또는 가볍게 정리해 제시합니다. 두 축은 일부러 나눈 것이므로(아래 _왜 두 축인가_) 항목을 합치거나 순위를 다시 매기지 않습니다.

마지막에 한 줄로 요약합니다. 축별 항목 수와 _각 축 안에서_ 가장 심각한 문제(있다면)입니다. 축을 가로질러 하나의 1위를 고르지 않습니다. 분리가 막으려던 것이 바로 그 재순위화입니다.

## 왜 두 축인가

변경은 한 축을 통과하고 다른 축에서 실패할 수 있습니다.

- 모든 규약을 지켰지만 엉뚱한 것을 구현한 코드 → **Standards 통과, Spec 실패.**
- 이슈가 요구한 대로 정확히 동작하지만 프로젝트 관례를 어긴 코드 → **Spec 통과, Standards 실패.**

따로 보고해야 한 축이 다른 축을 가리지 않습니다.
