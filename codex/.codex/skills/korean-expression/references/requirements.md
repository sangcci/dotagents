# 요구사항 문장

정책서의 규칙, 기획서의 요구사항, API 스펙의 처리 규칙, 설계서의 트랜잭션, 실패 처리와 검증, Issue의 완료 조건은 이 파일의 문장 틀로 쓴다. 문장 틀은 EARS(Easy Approach to Requirements Syntax)를, 품질 기준은 ISO/IEC/IEEE 29148을 한국어에 맞춘 것이다.

## 요구사항 문장의 구성

요구사항 문장 하나는 다음 요소로 구성한다.

- 조건: 요구사항이 적용되는 사건, 상태나 범위
- 주체: 응답하는 시스템이나 사람
- 응답: 주체가 하는 동작과 결과

### 작성 규칙

- 조건을 문장 앞에 쓰고, 주체와 응답을 뒤에 쓴다.
- 주체에는 보조사 `은`, `는`을 붙인다.
- 문장 하나에 응답 하나를 쓴다.
- 결과물에는 유형 레이블을 붙이지 않고 요구사항 문장만 쓴다.
- 기본 어미가 한다체가 아닌 결과물에서도 요구사항 문장의 구성과 틀은 같게 쓰고 어미만 바꾼다.

## 문장 틀

유형 이름은 EARS의 원래 이름을 쓴다.

| 유형 | EARS 키워드 | 쓰는 때 | 문장 틀 |
| --- | --- | --- | --- |
| Ubiquitous | 없음 | 조건 없이 항상 지키는 규칙 | `<주체>는 <응답>한다.` |
| Event-driven | When | 특정 사건이 일어나면 응답하는 규칙 | `<사건>하면 <주체>는 <응답>한다.` |
| State-driven | While | 특정 상태가 이어지는 동안 지키는 규칙 | `<상태>인 동안 <주체>는 <응답>한다.` |
| Unwanted behaviour | If, Then | 오류, 위반이나 실패에 응답하는 규칙 | `<오류 조건>이면 <주체>는 <응답>한다.` |
| Optional feature | Where | 특정 기능이나 범위에만 적용하는 규칙 | `<기능이나 범위>에서 <주체>는 <응답>한다.` |
| Complex | 키워드 조합 | 상태와 사건이 함께 필요한 규칙 | `<상태>인 동안 <사건>하면 <주체>는 <응답>한다.` |

다음 예시의 레이블은 유형을 설명하려고 이 파일에만 붙였다.

```text
Ubiquitous: 서버는 여행 참여 인원을 여행 정원 이하로 유지한다.
Event-driven: 회원이 초대 코드 검색 버튼을 누르면 앱은 초대 코드 검색 API를 호출한다.
State-driven: 여행이 확정 전인 동안 관리자는 초대 링크를 공유할 수 있다.
Unwanted behaviour: `countryCode`가 `ETC`가 아닌데 `customCountryName`이 있으면 서버는 `400 COMMON_INVALID_REQUEST`로 거절한다.
Optional feature: 1차 MVP에서 서버는 초대 코드를 다시 발급하지 않는다.
Complex: 여행이 확정 전인 동안 관리자가 참여자를 내보내면 서버는 그 회원의 지출 기록을 유지한다.
```

- Event-driven과 Unwanted behaviour는 둘 다 `-면`을 쓴다. Unwanted behaviour의 조건에는 오류, 위반이나 실패를 쓴다.
- Event-driven 규칙을 쓰면 그 사건의 Unwanted behaviour 규칙이 필요한지 확인한다. 실패 결과가 정해지지 않았으면 [정책 상태](usage/document.md#정책-상태)의 `논의 필요`로 남긴다.

## 의무 수준

| 의무 수준 | 주체가 시스템일 때 | 주체가 사람일 때 |
| --- | --- | --- |
| 반드시 함 | `-한다` | `-해야 한다` |
| 하도록 허용함 | 쓰지 않음 | `-할 수 있다` |
| 금지함 | `-하지 않는다` | `-할 수 없다` |

- 시스템의 동작에 `-할 수 있다`를 쓰지 않는다. 시스템이 동작하는 조건을 정해 Event-driven이나 State-driven으로 쓴다.
- `-하는 것이 좋다`, `-하도록 권장한다`, `-할 필요가 있다`를 쓰지 않는다. 의무인지 허용인지 정한다.

## 품질 기준

### 개별 요구사항

요구사항 문장마다 다음 9가지를 확인한다.

| 특성 | 기준 | 확인 질문 |
| --- | --- | --- |
| 필요성 | 빼면 기능이나 정책에 빈틈이 생김 | 이 문장을 지우면 무엇이 정해지지 않는가? |
| 적합성 | 문서의 수준에 맞음 | 정책서에 구현 세부 사항이나 API 필드를 쓰지 않았는가? |
| 명확성 | 한 가지로만 해석함 | 두 사람이 읽고 다른 동작을 구현할 여지가 없는가? |
| 완전성 | 문장 틀에 필요한 요소를 모두 씀. Ubiquitous는 조건 없이 주체와 응답만 씀 | 문장 틀에 필요한 요소 중 빠진 것이 없는가? |
| 단일성 | 응답 하나만 담음 | `그리고`, `또는`, 쉼표로 응답 두 개를 잇지 않았는가? |
| 실현 가능성 | 정한 범위와 기술로 만들 수 있음 | 아직 정하지 않은 기술이나 외부 조건에 기대지 않는가? |
| 검증 가능성 | 테스트나 관찰로 지켰는지 판단함 | 통과와 실패를 가르는 결과나 수치가 있는가? |
| 정확성 | 근거 자료와 맞음 | 회의 결론, 화면 정의서나 기존 정책과 어긋나지 않는가? |
| 준수성 | 이 파일의 문장 틀을 따름 | 문장 틀 6가지 중 하나로 썼는가? |

### 요구사항 집합

한 기능이나 업무 영역의 요구사항 전체에 대해 다음 5가지를 확인한다.

| 특성 | 확인 질문 |
| --- | --- |
| 완전성 | 정상 흐름의 사건마다 Unwanted behaviour 규칙이 있는가? |
| 일관성 | 두 규칙이 같은 조건에서 다른 응답을 정하지 않는가? |
| 실현 가능성 | 규칙 전체를 함께 지킬 수 있는가? |
| 이해 가능성 | 관련 문서를 읽지 않아도 규칙의 조건과 응답을 이해하는가? |
| 검증 가능성 | 규칙마다 확인할 테스트나 관찰 방법이 있는가? |

## 요구사항에 쓰지 않는 표현

ISO/IEC/IEEE 29148이 모호하다고 분류한 표현은 요구사항 문장에 쓰지 않는다.

| 분류 | 쓰지 않는 표현 | 대신 쓰는 내용 |
| --- | --- | --- |
| 최상급 | 최고, 최대한, 최소한, 가장 | 수치 상한이나 하한 |
| 주관적 표현 | 쉬운, 편리한, 빠른, 안정적인, 직관적인 | 측정할 결과와 수치 |
| 모호한 대명사 | 이것, 그것, 해당 | 대상의 이름 |
| 모호한 부사와 형용사 | 거의, 대부분, 일부, 상당히, 적절한, 충분한 | 수치나 대상 목록 |
| 열린 표현 | 지원한다, 처리한다(범위 없이), 등 | 지원 범위와 동작, 전체 목록 |
| 비교 표현 | 더 나은, 개선된, 향상된 | 비교 기준과 수치 |
| 빠져나갈 표현 | 가능하면, 필요시, 원칙적으로, 경우에 따라 | 조건을 정한 Event-driven이나 State-driven |
| 전체 표현 | 항상, 모든, 절대, 전혀(범위 없이) | 적용 범위를 정한 Ubiquitous |
