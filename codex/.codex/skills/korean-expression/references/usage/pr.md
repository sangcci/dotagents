# PR

Pull Request 본문에 적용한다. 기본 어미는 합니다체이고, 예시 블록은 변경형을 쓴다.

## 공통 규칙

- 저장소의 PR 템플릿이 있으면 템플릿의 섹션을 따른다. 템플릿이 없으면 이 파일의 섹션을 쓴다.
- 섹션 제목은 `##`로 쓰고 이모지와 구분선을 쓰지 않는다.
- 내용이 없는 섹션은 지우지 않고 `없음`과 이유 한 문장을 쓴다. `변경 예시`와 `세부 사항`은 예외로, 내용이 없으면 섹션을 지운다.
- 저장소 템플릿은 이 파일의 섹션 뒤에 브랜치와 리뷰어 지정 같은 절차 확인 목록을 둘 수 있다.
- PR을 읽는 리뷰어는 작성 과정의 대화를 보지 않았다고 보고 쓴다.
- diff에서 확인하는 파일 목록, 코드와 구현 순서는 본문에 쓰지 않는다.
- 이슈, 기획과 정책서에 있는 내용은 다시 쓰지 않고 링크한다.
- AI 도구의 이름이나 생성 표기를 쓰지 않는다.

## 단위

- PR 하나에는 리뷰어에게 요청하는 판단 하나를 담는다. 이 판단을 `변경 요약`의 마지막 문장에 쓴다.
- 코드 PR은 테스트 코드, 생성된 코드와 lock 파일을 뺀 변경을 400줄 이하로 만든다. 400줄을 넘으면 선행 PR 위에 다음 PR을 쌓아 나눈다.
- 문서 PR은 업무 하나의 정책서, API 스펙과 설계서 변경을 함께 담는다.
- Issue 하나를 PR 여러 개로 나눌 수 있다. PR 하나로 Issue 여러 개를 닫지 않는다.
- 기능 변경, 리팩터링, 대규모 포맷 변경과 의존성 갱신은 서로 다른 PR로 만든다.

## 제목

- 저장소의 제목 규칙이 있으면 따른다.
- 규칙이 없으면 `<type>: <대상과 바꿀 내용>`으로 쓴다. 변경 방법이 아니라 변경 대상과 결과를 쓴다.
- 50자 이하로 쓰고 끝에 마침표를 찍지 않는다.
- PR을 Squash merge하면 PR 제목이 커밋 제목이 된다. PR 제목은 저장소의 커밋 제목 규칙을 따른다.

## 분량

- `<details>` 밖의 본문은 코드 블록을 빼고 800자 이하로 쓴다.
- 800자를 넘으면 세부 근거와 변경 위치를 `<details>`로 접는다.
- 오탈자, 서식과 이름만 바꾸는 PR은 `변경 요약`만 한 문장으로 쓴다. `변경 예시`와 `세부 사항`은 지우고, 나머지 섹션에는 `없음`을 쓴다.

## 섹션

| 섹션 | 내용 | 형태 |
| --- | --- | --- |
| 관련 Issue | 완료하는 Issue와 관련 Issue | `Closes #번호`, `Related #번호` |
| 변경 요약 | 무엇을 왜 바꿨는지와 리뷰어가 판단할 내용 | 문단, 3문장 이하 |
| 변경 예시 | 바뀐 동작이나 기준 | [변경형 예시 블록](../example-blocks.md#변경형) |
| 리뷰 포인트 | 리뷰어의 판단이 필요한 결정, 호환성, 배포 순서, 다른 문서와 구현에 주는 영향 | 문장 목록 |
| 검증 결과 | 실행한 검증과 결과, 실행하지 못한 검증과 이유 | 도입 문장과 보충 목록 |
| 세부 사항 | 변경 위치, 대안 비교, 긴 근거 | `<details>` |

- `변경 요약`의 마지막 문장은 리뷰어에게 판단을 요청하는 `-해 주세요` 문장으로 쓴다.
- 문서 PR은 `변경 요약`의 첫 문장에 확정한 결정을 반영하는지, 새 기준을 제안하는지 쓴다.
- 동작이나 기준이 바뀌지 않으면 `변경 예시` 섹션을 지운다.
- `리뷰 포인트`에는 구현 설명을 반복하지 않는다. 가이드를 따르지 않았으면 이유를 쓴다.
- `검증 결과`는 검사 이름과 결과를 명사형으로 쓴다. 재현에 필요하지 않으면 전체 명령, 실행 환경과 로그를 쓰지 않는다.
- 실행하지 못한 검증은 `-하지 못했습니다` 문장과 이유로 쓴다.
- 문서 링크 검사나 SQL 조건의 정적 확인을 실제 DB 동작이나 동시성 검증으로 쓰지 않는다.
- Issue와 범위가 달라지거나 필요한 검증이 실패했으면 PR을 만들기 전에 요청자에게 알리고 진행 여부를 확인받는다.

## 작성 예시

다음은 가상 예시입니다.

````markdown
## 관련 Issue

Closes #31

## 변경 요약

`countryCode`가 `ETC`가 아닌데 `customCountryName`을 보낸 요청을 `400`으로 거절하는 기준을 제안합니다. 서버가 이 요청을 무시하면 클라이언트가 국가명을 비우지 않는 결함이 드러나지 않습니다. 무시하지 않고 거절하는 판단이 맞는지 확인해 주세요.

## 변경 예시

```http
# 여행 생성: 기타 국가가 아닌데 국가명을 보냄
POST /api/v1/trips
{ "countryCode": "JP", "customCountryName": "베트남", ... }

# As-is: 기준 없음
# To-be
400 COMMON_INVALID_REQUEST
```

## 리뷰 포인트

- 이 기준은 `USER-03`의 조건부 필드 거절 규칙과 같은 방식입니다.
- 기준을 정하면 서버 OpenAPI의 `trip.yml`에 같은 기준을 반영해야 합니다.

## 검증 결과

다음 검증을 실행했습니다.

- 문서 링크의 대상이 있는지 확인함
- API 목록과 본문의 오류 코드가 같은지 확인함

<details>
<summary>세부 사항</summary>

| 문서 | 위치 | 내용 |
| --- | --- | --- |
| `api-spec/trip.md` | `TRIP-02 여행 생성` 오류 표 | 생성 요청 거절 규칙 |
| `api-spec/trip.md` | `TRIP-04 여행 정보 수정` 오류 표 | 최종 `countryCode` 기준 거절 |

</details>
````
