# 설계서

정책서의 업무 규칙을 구현하는 데이터, 쿼리, 트랜잭션과 처리 흐름을 정하는 문서에 적용한다. 문서 유형은 [문서](document.md#문서-유형)의 레퍼런스이고, 기본 어미는 한다체다.

## 원칙

- 설계서에는 팀이 정한 구조를 구현 여부와 관계없이 쓴다. 구현 진행 상황은 구현 저장소의 Issue와 PR에서 관리한다.
- 업무 규칙은 정책서를 링크하고 설계서에 다시 쓰지 않는다.

## 쓰지 않는 섹션

다음 섹션은 설계서에 쓰지 않는다. 표의 내용은 오른쪽 위치로 옮긴다.

| 쓰지 않는 섹션 | 옮기는 위치 |
| --- | --- |
| 회의 결정, 설계 결정, 결정한 방향 | 결정이 적용되는 절의 본문 한 문장과 [근거 링크](#결정의-이유) |
| 구현 상태, 구현 PR 목록 | 구현 저장소의 Issue와 PR |
| 변경 이력, 변경 목록 | 문서를 바꾼 PR |
| 제안, 후보, 구현 제안 | 논의 Issue, 설계를 제안하는 PR |
| 구현 시 검증, 구현 전 결정 | [구조](#구조)의 검증 섹션, 논의 Issue |

## 새 설계서를 만드는 조건

- 새 업무 영역이나 하위 시스템이 생기면 새 설계서를 만든다.
- 그 밖의 설계 변경은 기존 설계서를 갱신한다.
- 설계서 목록의 범위와 겹치는 설계서를 만들지 않는다. 설계서 목록은 문서 이름과 범위를 표로 관리한다.

## 구조

다음 순서로 쓴다. 내용이 없는 섹션은 쓰지 않는다.

| 섹션 | 내용 | 형태 |
| --- | --- | --- |
| 개요 | 설계서의 범위와 관련 정책서 | 문단, 3문장 이하 |
| 저장 데이터 | 테이블, 컬럼, 제약과 키 | 표 |
| 처리 흐름 | 요청부터 응답까지의 순서 | 순서 다이어그램과 문장 목록 |
| 쿼리 | 핵심 조회와 갱신 쿼리 | `sql` 블록 |
| 트랜잭션과 동시성 | 트랜잭션 범위, 잠금과 충돌 처리 | 요구사항 문장 목록 |
| 실패 처리 | 실패 조건과 결과 | 요구사항 문장 목록 |
| 검증 | 테스트로 확인할 조건 | 요구사항 문장 목록 |

- 하위 시스템이 둘 이상이면 하위 시스템마다 `##` 절을 두고, 그 안에서 `###`로 위 순서를 따른다. `####`가 필요하면 설계서를 나눈다.
- 개요에는 설계서가 다루는 범위와 다루지 않는 범위를 쓰고 관련 정책서의 절을 링크한다.
- 저장 데이터 표의 열은 이름, 타입, 제약, 뜻 순서로 쓴다. NULL을 허용하는 컬럼은 `뜻`에 NULL의 의미를 쓴다. 정하지 않은 컬럼은 표에 쓰지 않는다.
- 처리 흐름은 [순서 다이어그램](../example-blocks.md#순서-다이어그램)으로 쓴다. 다이어그램의 조건과 롤백 범위는 쿼리와 트랜잭션 섹션의 내용과 같게 쓴다.
- 쿼리 블록 앞에는 쿼리가 하는 일을 한 문장으로 쓴다. 파라미터, 권한을 확인하는 위치와 쿼리가 속한 트랜잭션을 쓴다.
- 트랜잭션과 동시성, 실패 처리, 검증의 문장은 [요구사항 문장](../requirements.md)의 문장 틀로 쓴다.
- 실패 처리에는 조건부 갱신이 0건인 결과와 SQL 오류를 나누어 쓴다.
- 검증에는 테스트로 확인할 조건을 쓴다. `-하는지 확인한다`로 쓰지 않고, 통과했을 때의 동작을 쓴다. 테스트 실행 결과는 PR의 `검증 결과`에 쓴다.

```diff
# 검증 문장의 형식 (가상 예시)
- 가입 전용 토큰으로 일반 회원 API를 요청하면 거절되는지 확인한다.
+ 가입 전용 토큰으로 일반 회원 API를 요청하면 서버는 `401`로 거절한다.
```

## 결정의 이유

결정의 이유는 그 결정이 적용되는 위치에 한 문장으로 쓰고, 결정을 기록한 Issue의 `논의 결과`나 제안 PR 하나를 링크한다. 회의 날짜, 참석자와 논의 경과는 쓰지 않는다. 다음은 가상 예시다.

```markdown
지출 수정 잠금은 DB 행 잠금을 쓴다. 근거: [Issue #21 논의 결과](https://github.com/...)
```

## 정하지 않은 내용

- 정하지 않은 내용은 [정책 상태](document.md#정책-상태)의 상태 인용문으로 쓴다.
- `> 논의 필요` 인용문에는 논의 Issue 번호를 붙인다. 논의 Issue가 없으면 Issue를 먼저 만든다.
- 상태 인용문은 그 내용이 적용되는 절 바로 아래에만 쓴다. 문서 끝에 다시 모으지 않는다.
- `##` 절의 절반 넘게 `> 논의 필요` 인용문이 있으면 설계서를 병합하지 않는다. 논의 Issue에서 먼저 정하고 설계서를 쓴다.

## 예시

- 예시는 [예시 블록](../example-blocks.md#확정형)의 확정형으로 쓴다.
- 인물, ID와 시각은 블록 앞 문장에 가상 예시라고 밝힌다.
- 정하지 않은 내용에 따라 결과가 달라지면 결론을 고르지 않고, 같은 입력에서 무엇이 달라지는지 보여 준다.

## 분량과 적용 시점

- 설계서는 300줄 이하로 쓴다. 300줄을 넘으면 하위 시스템별로 설계서를 나누고, 원래 설계서에는 개요와 링크만 남긴다.
- 이 규칙은 새로 만드는 설계서와 새로 수정하는 절에 적용한다. 수정하지 않는 절은 기존 내용을 유지한다.
- 300줄을 넘는 기존 설계서의 절을 수정하는 PR에서는 설계서를 나누지 않는다. 설계서를 나누는 작업은 별도 PR로 한다.

## 완료 전 확인

다음 항목은 새로 만든 설계서와 이번 PR에서 수정한 절에 적용한다.

- 설계서에 구현 진행 상황, 회의 경과와 변경 이력이 없는가?
- 섹션이 정한 순서를 따르는가?
- 정책서의 업무 규칙을 다시 쓰지 않고 링크했는가?
- 결정의 이유가 한 문장이고 논의 Issue나 PR을 링크했는가?
- `논의 필요` 인용문마다 논의 Issue 번호가 있는가?
- 트랜잭션, 실패 처리와 검증이 요구사항 문장인가?
- 다이어그램, 쿼리와 본문의 조건이 같은가?
- 300줄 이하인가?
