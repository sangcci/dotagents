# 설계서

정책서의 업무 규칙을 구현하는 현재의 데이터, 쿼리, 트랜잭션과 처리 흐름을 정하는 문서에 적용한다. 문서 유형은 [문서](document.md#문서-유형)의 레퍼런스이고, 기본 어미는 한다체다.

## 원칙

- 설계서에는 현재 구조만 쓴다. 결정 과정, 회의 내용과 구현 진행 상황을 쓰지 않는다.
- 업무 규칙은 정책서를 링크하고 설계서에 다시 쓰지 않는다.
- 결정의 이유는 그 결정이 적용되는 위치에 한 문장으로 쓰고, 결정을 기록한 Issue의 `논의 결과`나 제안 PR 하나를 링크한다.
- 정하지 않은 내용은 [정책 상태](document.md#정책-상태)의 `> 논의 필요` 인용문으로 쓰고 논의 Issue를 링크한다.

```markdown
지출 수정 잠금은 Redis 대신 DB 행 잠금을 쓴다. 근거: [Issue #21 논의 결과](https://github.com/...)
```

## 새 설계서를 만드는 조건

- 새 도메인이나 하위 시스템이 생기면 새 설계서를 만든다.
- 그 밖의 설계 변경은 기존 설계서를 갱신한다.
- 설계서 목록의 범위와 겹치는 설계서를 만들지 않는다. 설계서 목록은 문서 이름과 범위를 표로 관리한다.

## 쓰지 않는 섹션

다음 섹션은 설계서에 쓰지 않는다.

- 회의 결정, 설계 결정, 결정한 방향
- 구현 상태, 구현 PR 목록
- 변경 이력, 변경 목록
- 제안, 후보

## 구조

다음 순서로 쓴다. 내용이 없는 섹션은 쓰지 않는다.

| 섹션 | 내용 | 형태 |
| --- | --- | --- |
| 개요 | 설계서의 범위와 관련 정책서 | 문단, 3문장 이하 |
| 저장 데이터 | 테이블, 컬럼, 제약과 키 | 표 |
| 처리 흐름 | 요청부터 응답까지의 순서 | 순서 다이어그램과 문장 목록 |
| 쿼리 | 핵심 조회와 갱신 쿼리 | `sql` 블록 |
| 트랜잭션과 동시성 | 트랜잭션 범위, 잠금과 충돌 처리 | 요구사항 문장 목록 |
| 실패 처리 | 실패 조건과 결과 | 요구사항 문장 목록 |
| 검증 | 테스트로 확인할 조건 | 요구사항 문장 목록 |

- 트랜잭션과 동시성, 실패 처리, 검증의 문장은 [요구사항 문장](../requirements.md)의 문장 틀로 쓴다.
- 저장 데이터 표의 열은 이름, 타입, 제약, 뜻 순서로 쓴다.
- 쿼리 블록 앞에는 쿼리가 하는 일을 한 문장으로 쓴다.

## 분량

- 설계서는 300줄 이하로 쓴다. 300줄을 넘으면 하위 시스템별로 설계서를 나누고 원래 설계서에는 개요와 링크만 남긴다.
