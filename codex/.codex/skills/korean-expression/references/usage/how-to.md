# How-to

할 일이 정해진 독자가 따라 하며 작업을 끝내는 문서에 적용한다. 적용 절차, 운영 절차와 트러블슈팅을 포함한다. 문서 유형은 [문서](document.md#문서-유형)의 How-to이고, 기본 어미는 한다체다.

## 원칙

- 독자는 작업의 목적을 알고 있다고 보고 쓴다. 개념과 이유를 설명하지 않고, 설명 문서를 개요에 링크한다.
- 작업 하나를 끝내는 데 필요한 내용만 쓴다. 옵션 전체 목록은 레퍼런스를 링크한다.
- 독자가 명령과 값을 복사해 그대로 실행하게 쓴다.

## 제목

- `<작업>하는 방법` 명사구로 쓴다. 예를 들어 `Terraform state 버킷을 적용하는 방법`처럼 쓴다.
- 트러블슈팅은 `<증상이나 오류 메시지> 해결 방법`으로 쓴다.

## 구조

다음 순서로 쓴다.

| 섹션 | 내용 | 형태 |
| --- | --- | --- |
| 개요 | 작업의 결과, 실행하는 사람과 설명 문서 링크 | 문단, 3문장 이하 |
| 사전 조건 | 필요한 권한, 도구와 끝나 있어야 하는 작업 | 도입 문장과 보충 목록 |
| 절차 | 작업 단계 | 번호 문장 목록 |
| 확인 | 작업이 끝났는지 확인하는 방법 | 문장과 기대 출력 블록 |
| 되돌리기 | 작업 전 상태로 돌아가는 방법 | 번호 문장 목록 |

- 운영 환경, 공유 리소스나 권한을 바꾸는 작업에는 `되돌리기`를 쓴다. 되돌릴 수 없으면 `되돌리기`에 `되돌릴 수 없다.`와 이유를 쓴다.
- 작성 중에 실제로 겪은 오류가 있으면 `확인` 다음에 `문제 해결` 섹션을 두고 오류마다 증상과 해결을 쓴다.

## 절차

- 단계 하나에는 동작 하나를 쓴다.
- 단계는 15개 이하로 쓴다. 더 많으면 작업을 나눠 How-to를 여러 개 쓴다.
- 명령은 [명령과 출력](../example-blocks.md#명령과-출력) 블록으로 쓴다.
- 실행하는 사람이 단계마다 다르면 단계 문장의 주어로 실행하는 사람을 쓴다.
- 조건에 따라 동작이 갈리면 `<조건>이면 <동작>한다.` 문장으로 쓴다. 갈리는 길이 3개 이상이면 길마다 문서를 나눈다.
- 되돌릴 수 없는 단계 바로 앞에는 `> 주의` 인용문을 두고, 실행 결과와 실행 전에 확인할 것을 쓴다.

```markdown
> 주의
>
> 이 단계는 공용 IAM 사용자의 Access Key를 삭제한다. 실행 전에 앱과 CI가 이 키를 쓰지 않는지 확인한다.
```

## 여러 날에 걸친 작업

운영 전환처럼 단계마다 확인 기간이 필요한 작업은 다음 두 종류의 문서로 나눈다.

- 전체 순서 문서: 단계 이름, 실행하는 사람, 시작 조건과 단계별 How-to 링크를 담은 표
- 단계별 How-to: 단계 하나의 사전 조건, 절차, 확인과 되돌리기

전체 순서 문서의 표는 단계, 단계 이름, 실행, 시작 조건, 문서 열로 쓰고 셀마다 값 하나만 쓴다. 단계 이름은 명사구로, 시작 조건은 `-ㅁ`, `-음` 명사형으로 쓴다. 절차와 이유는 단계별 How-to와 설명 문서에 쓴다.

| 단계 | 단계 이름 | 실행 | 시작 조건 | 문서 |
| --- | --- | --- | --- | --- |
| 1 | state 버킷 적용 | admin | 첫 admin 계정을 만듦 | Terraform state 버킷을 적용하는 방법 |
| 2 | 팀원 IAM 사용자 적용 | admin | 1단계 결과를 확인함 | 팀원 IAM 사용자를 적용하는 방법 |

## 트러블슈팅

트러블슈팅 문서는 다음 순서로 쓴다.

| 섹션 | 내용 | 형태 |
| --- | --- | --- |
| 증상 | 사용자가 본 현상과 오류 메시지 원문 | 문장과 `text` 블록 |
| 원인 | 증상이 생기는 원인 | 문단, 3문장 이하 |
| 해결 | 원인을 없애는 단계 | 번호 문장 목록 |
| 확인 | 증상이 사라졌는지 확인하는 방법 | 문장과 기대 출력 블록 |

- 원인이 둘 이상이면 원인마다 `### 원인: <원인>` 절을 두고 그 아래에 해결과 확인을 쓴다.
- 원인을 확인하지 못했으면 `원인`에 `원인을 확인하지 못했다.`와 확인한 범위를 쓴다.
