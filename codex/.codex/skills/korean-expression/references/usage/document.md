# 문서

저장소에 두는 문서에 적용한다. 기본 어미는 한다체다. 문서를 쓰기 전에 문서 유형을 정하고, 유형별 파일을 함께 읽는다.

## 문서 유형

문서 유형은 독자가 문서를 읽는 상황으로 정한다.

| 유형 | 독자의 상황 | 독자의 질문 | 문서 | 규칙 |
| --- | --- | --- | --- | --- |
| 튜토리얼 | 처음 배우면서 따라 함 | 처음에 무엇을 해 보면 되는가 | 입문, 실습 | [튜토리얼](tutorial.md) |
| How-to | 할 일이 정해져 있고 따라 함 | 이 작업을 어떻게 하는가 | 적용 절차, 운영 절차, 트러블슈팅 | [How-to](how-to.md) |
| 레퍼런스 | 작업 중에 정확한 기준을 찾음 | 기준과 값이 무엇인가 | 정책서, 기획서, API 스펙, 설계서, 규칙 가이드, 용어집 | 이 파일, [설계서](design.md) |
| 설명 | 읽고 이해하려 함 | 왜 이렇게 하는가 | 배경, 개념, 구조 선택의 이유, 전환 설계 | [설명 문서](article.md) |

유형이 헷갈리면 다음 두 질문으로 정한다.

| 독자가 읽으면서 | 배우는 중 | 일하는 중 |
| --- | --- | --- |
| 손을 움직임 | 튜토리얼 | How-to |
| 읽기만 함 | 설명 | 레퍼런스 |

- 문서 하나에는 유형 하나만 쓴다. 다른 유형의 내용이 필요하면 별도 문서로 쓰고 링크한다.
- 튜토리얼과 How-to에 설명을 넣지 않는다. 이유는 설명 문서에 쓰고 링크한다.
- 설명 문서에 절차와 레퍼런스 표를 넣지 않는다. 절차는 How-to에, 기준과 값은 레퍼런스에 쓰고 링크한다.
- 레퍼런스에 절차와 학습 내용을 넣지 않는다.

## 공통 규칙

- 문서 제목 바로 아래에 개요를 3문장 이하로 쓴다. 개요에는 문서를 읽은 독자가 할 수 있는 일이나 알게 되는 내용을 쓴다.
- 문서 하나에는 주제 하나를 쓴다. 제목은 `###`까지 쓰고, `####`가 필요하면 문서를 나눈다.
- 독자가 판단하거나 작업하는 데 필요한 내용만 쓴다. 문서의 역할을 되풀이하는 안내와 면책 문구를 쓰지 않는다.
- 같은 내용을 여러 문서에 복제하지 않는다. 기준을 관리하는 문서 하나에 쓰고 다른 문서에서 링크한다.
- 다른 문서의 특정 위치를 가리키면 커밋을 고정한 링크를 쓴다.
- 문서와 구현이 다르면 현재 구현을 기준으로 문서를 고치지 않는다. 차이를 `논의 필요`로 남기고, 정한 결과에 따라 문서와 구현을 함께 고친다.
- 정하지 않은 내용을 기존 코드나 관례로 채우지 않는다.
- 튜토리얼, How-to와 레퍼런스에는 현재 기준만 쓴다. 변경 이력과 결정 과정은 Issue와 PR에 쓰고 문서에서 링크한다.
- 레퍼런스에는 구현 진행 상황을 쓰지 않는다. 구현 여부와 배포 여부는 구현 저장소의 Issue와 PR에서 확인한다.

## 정책서

정책서는 화면, API와 구현이 따라야 하는 업무 조건과 결과를 정한다.

### 정책서의 범위

- 업무 조건과 사용자가 관찰하는 결과를 쓴다.
- 테이블, 필드, 타입, 토큰 구조와 프레임워크 설정을 쓰지 않는다. 이 내용은 설계서, API 스펙이나 코드에서 관리한다.
- 선택의 이유와 대안 비교를 쓰지 않는다. 이 내용은 Issue의 논의 결과나 설명 문서에서 관리한다.
- 필드명, enum과 역할 코드 대신 업무 용어를 쓴다.

### 정책서의 구조

- 대분류는 화면, API나 세부 기능이 아니라 업무 영역으로 나눈다.
- 문서 제목과 개요 아래에 목차를 둔다. 목차의 항목은 본문의 제목으로 링크한다.
- 대분류는 업무 흐름 순서로 배치한다.
- 각 영역은 다른 영역을 읽지 않아도 이해하도록 쓴다. 다른 영역의 기준이 필요하면 그 영역의 제목을 링크한다.
- 각 영역은 핵심 규칙, 적용 조건과 예외, 적용 예시 순서로 쓴다.

```markdown
# 인증 정책서

회원의 로그인과 인증 유지에 적용하는 업무 규칙이다.

## 목차

- [로그인](#로그인)
  - [인증 실패](#인증-실패)
- [인증 유지](#인증-유지)
  - [토큰 갱신](#토큰-갱신)

## 로그인

### 인증 실패
```

### 규칙과 예시

- 규칙은 [요구사항 문장](../requirements.md)의 문장 틀로 쓴다.
- 경우가 5개를 넘으면 같은 문장을 반복하지 않고 의사결정표를 쓴다.
- 복잡하거나 오해하기 쉬운 규칙에는 [적용 예시](../example-blocks.md#적용-예시)를 둔다.

### 권한 매트릭스

역할별로 허용 여부를 비교해야 하면 영역의 첫 부분에 권한 매트릭스를 둔다.

- 행은 기능, 열은 역할로 쓴다.
- 셀에는 `허용`과 `불가`만 쓴다.
- 조건과 예외는 표 아래에 요구사항 문장으로 쓴다.

### 정책 상태

확정하지 않은 내용은 확정한 규칙과 섞지 않고 다음 표의 상태로 표시한다.

| 상태 | 뜻 | 쓰는 위치 |
| --- | --- | --- |
| 확정 | 정해서 현재 적용하는 내용 | 영역의 본문 |
| 논의 필요 | 현재 범위에서 정해야 하는 내용 | 영역 바로 아래의 `> 논의 필요` 인용문 |
| 추후 반영 | 반영하기로 정했지만 현재 범위에 넣지 않은 내용 | 영역 바로 아래의 `> 추후 반영` 인용문 |
| 추후 검토 | 현재 범위 밖에서 도입 여부를 검토할 내용 | 영역 바로 아래의 `> 추후 검토` 인용문 |

- 인용문의 첫 줄에는 상태 이름만 쓰고, 빈 인용 줄 다음에 내용을 쓴다.
- 정할 선택지는 `A vs B` 형식의 명사형으로 쓴다.
- 논의 Issue가 있으면 내용 끝에 Issue를 링크한다. 설계서는 [설계서](design.md#정하지-않은-내용)에 따라 Issue 링크를 반드시 붙인다.
- 검토 중인 구현 방식과 컬럼 후보는 상태 인용문으로 쓰지 않는다. 논의 Issue나 제안 PR에서 다룬다.
- 확인할 자료가 남았으면 `논의 필요`에 확인할 사람과 대상을 쓴다.
- 정하면 상태 인용문을 지우고 규칙을 본문에 쓴다. 결정의 이유는 논의 Issue의 `논의 결과`나 결정 근거를 남긴 PR을 링크한다.

```markdown
> 논의 필요
>
> 일반 로그인 세션을 하루 동안 유지함 vs 브라우저를 닫으면 만료함 (#12)
```

## 기획서

기획서는 기능 하나의 목표, 범위와 요구사항을 정한다. 다음 순서로 쓴다.

| 섹션 | 내용 | 형태 |
| --- | --- | --- |
| 목표 | 기능으로 이루려는 결과 | 문단, 3문장 이하 |
| 범위 | 포함 범위와 제외 범위 | 보충 목록 두 개 |
| 사용자 시나리오 | 기능의 주요 흐름 | [사용자 시나리오](../example-blocks.md#사용자-시나리오) 블록 |
| 요구사항 | 기능이 지켜야 하는 규칙 | [요구사항 문장](../requirements.md) 문장 목록 |
| 미결정 사항 | 정하지 않은 내용 | `> 논의 필요` 인용문 |

## 규칙 가이드와 README

규칙 가이드는 작업 규칙과 작성 규칙을 모은 레퍼런스다.

- 규칙을 먼저 쓰고, 선택이 헷갈리는 곳에는 피할 예시와 권장 예시를 둔다.
- 예시 아래에는 결과가 달라지는 이유와 그대로 적용하면 안 되는 조건만 쓴다.
- 가상 예시는 사례 이름이나 앞 문장에 `가상 예시`라고 밝힌다.
- 구현 경로와 명령은 현재 저장소에서 확인한 것만 쓴다.
- 작업 절차는 규칙 가이드에 쓰지 않고 How-to로 쓴다.
- README에는 저장소의 개요와 문서 목록만 쓴다. 문서 목록은 문서 이름과 범위를 표로 쓴다.

## 문서의 경계

| 내용 | 관리하는 문서 |
| --- | --- |
| 업무 조건과 사용자가 관찰하는 결과 | 정책서 |
| 기능의 목표, 범위와 요구사항 | 기획서 |
| 요청, 응답, 상태 코드와 필드 계약 | API 스펙 |
| 팀이 정한 데이터, 쿼리, 트랜잭션과 처리 흐름 | 설계서 |
| 결정의 배경, 검토한 선택지와 이유 | 논의 Issue의 `논의 결과`, 제안 PR |
| 구현 진행 상황과 검증 결과 | 구현 저장소의 Issue와 PR |
| 구조 선택의 맥락과 개념의 동작 원리 | 설명 문서 |
| 작업을 끝내는 순서 | How-to |
| 화면 구성과 사용자의 화면 이동 | Figma의 [화면 설명](screen.md). 저장소에는 화면 정의서를 쓰지 않음 |
