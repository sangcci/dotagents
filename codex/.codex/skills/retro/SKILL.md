사용자가 **회고**를 요청했습니다. 앞으로의 실행이 나아지도록 코딩 에이전트의 **환경**을 개선하는 방안을 제안합니다. 코드를 고치는 일이 아닙니다.

## 절차

1. 사용자가 지정한 세션의 1차 자료를 읽습니다. 이 기기의 세션 로그를 검색해야 할 수 있습니다. 지정하지 않았다면 현재 세션을 대상으로 합니다.

2. 다음 범주에서 개선 후보를 찾습니다.

- **탐색**: 에이전트가 올바른 파일을 찾기 쉬웠는가? 파일 사이에 숨은 의존성이 있는가? **탐색 포인터**가 있으면 쉬워지는가? _언제 쓰나_: 어떤 정보를 찾느라 세션이 오래 걸렸을 때.
- **자동 검사**: 에이전트가 낸 실수를 잡을 자동 검사가 있는가? 린트, 타입, 테스트, 파일시스템 린터? 먼저 repo 자체의 검사 명령(`package.json`이나 빌드 도구의 `lint`와 `check` 스크립트, CI 워크플로)을 읽습니다. 이미 있는데 연결되지 않았거나 조용히 깨진 검사가 있다면 새로 만드는 것이 아니라 그것이 발견입니다. 가드레일이 전혀 없는 repo(pre-commit 훅도 없고 lint, typecheck, test를 돌리는 CI 작업도 없음)는 그 자체로 발견입니다. 린트가 없는 repo는 중립적인 기본값이 아니라 계속 놓치고 있는 기회입니다. _언제 쓰나_: 자동 검사가 잡을 수 있었던 실수를 에이전트가 냈을 때, 또는 repo에 가드레일이 전혀 없을 때.
- **코딩 규약**: **리뷰어 에이전트**에게 새 규칙을 줘야 하는가? 기존 규칙을 없애거나 명확히 해야 하는가? 먼저 위반을 분류합니다. **기계적** 위반(고정된 구문 패턴, 금지된 API, import 모양, 파일 위치 규칙)은 결정적 검사를 만들고 끝냅니다. repo의 언어와 기존 가드레일에서 가장 싼 쪽, 곧 자체 린터의 커스텀 규칙, 새 pre-commit 훅, 새 CI 작업 중 하나입니다. 규칙을 쓰기보다 검사를 만드는 쪽이 기본값입니다. `CODING_STANDARDS.md` 같은 규약 문서는 진짜 **판단**이 필요한 경우(파일 간 일관성, "주변 스타일과 맞는가", 어떤 가드레일로도 대체할 수 없는 것)에만 둡니다. _언제 쓰나_: 리뷰어 에이전트가 실수를 잡지 못했을 때.
- **전역 지침 파일**: 코딩 규약(또는 자동 검사)으로 옮겨야 할 지침이 있는가? _언제 쓰나_: repo나 사용자의 전역 범위에 있는 `AGENTS.md` 같은 지침 파일이 특히 클 때.
- **도구 경제성**: 에이전트가 간소화할 수 있는 비싼 도구 호출을 했는가? 토큰 효율이 특히 나쁜 커스텀 도구(CLI, MCP)가 있는가? _언제 쓰나_: 에이전트가 비싼 도구 호출을 했을 때.
- **무효 지침**: 지침 파일에서 에이전트의 행동을 바꾸지 않는 지시를 찾습니다. _언제 쓰나_: 지침 파일이 크고 다루기 힘들 때.
- **정보 접근**: 에이전트가 쓸 수 있는 정보를 늘릴 기회를 찾습니다. 개발 서버 로그를 파일로 내보내기, 서드파티 서비스의 읽기 전용 접근이 예입니다. _언제 쓰나_: 결정적인 정보를 에이전트가 얻지 못했을 때.

3. 후보를 심각도 순으로 사용자에게 제시합니다.

## 참고

### 구현과 리뷰

모든 작업은 구현과 리뷰 두 단계를 거칩니다. 구현 에이전트는 **컨텍스트 압박**이 가장 큽니다. 탐색, 코드 작성, 실패 디버깅을 맡기 때문입니다.

리뷰 에이전트는 컨텍스트 압박이 가장 작습니다. diff를 받으므로 탐색이 필요 없고, 코드를 쓰거나 디버깅할 일이 대개 없습니다.

따라서 코딩 규약을 강제하는 책임은 구현 에이전트가 아니라 리뷰 에이전트에게 있어야 합니다.

### 파일

repo에서 다음 파일을 다룰 수 있습니다.

- `CLAUDE.md`와 `AGENTS.md`: 이 repo에서 일하는 모든 에이전트의 컨텍스트에 밀어 넣는 파일입니다. 극도로 아껴 써야 하며, 보통 다른 파일을 가리키는 **탐색 포인터**만 둡니다.
- `CODING_STANDARDS.md`: 구현이 아니라 리뷰 때 읽는 파일입니다. 규약이 1,000줄을 넘으면 docs 폴더로 가는 **탐색 포인터**를 둡니다.
- 문서: 다른 파일이 가리키는 참조 파일로 씁니다. 새로 쓰기 전에 기존 문서를 찾아봅니다.
- 스킬: 설명이 에이전트의 컨텍스트에 들어가므로 문서를 스킬로 둘 수 있고, 사용자가 호출하는 명령에도 스킬을 씁니다.
