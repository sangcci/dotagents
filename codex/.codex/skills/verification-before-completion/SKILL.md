# Verification Before Completion

완료 여부는 자신감이나 변경 사실이 아니라 검증 결과로 판단합니다. 마지막 관련 변경 이후의 근거가 없는 성공 주장은 하지 않습니다.

## 검증과 보고

1. 보고할 주장과 그 주장을 확인할 검증을 정합니다. 테스트 통과, 빌드 성공, 원래 문제 해결, 요구사항 충족을 각각 구분합니다.
2. 변경의 영향과 저장소 지침에 맞는 검증을 실행합니다. 문장이나 설정의 작은 변경은 파일 내용과 형식 확인으로 충분할 수 있습니다. 해당 변경과 무관한 테스트를 추가하지 않습니다.
3. 실행이 끝났는지 확인하고 종료 코드, 검사 범위, 실패 여부를 읽습니다. 실행 중인 명령, 일부 로그, 실행하지 않은 명령을 성공 근거로 삼지 않습니다.
4. 검증 결과와 실제 변경을 요청한 요구사항에 대조합니다. 검증이 확인하지 못한 부분은 완료된 것으로 확대하지 않습니다.
5. 확인한 결과를 보고합니다. 실패하거나 실행할 수 없었다면 그 사실과 이유, 확인된 범위, 남은 작업을 구분합니다.

## 근거의 범위

- 테스트가 통과했다고 하려면 해당 테스트 실행 결과가 필요합니다. 일부 테스트 통과를 전체 테스트 통과로 표현하지 않습니다.
- 빌드 성공에는 빌드 결과가 필요합니다. 린트나 포맷 검사 성공으로 대신하지 않습니다.
- 버그 해결에는 원래 증상이나 관련 동작을 확인한 근거가 필요합니다. 코드를 수정한 사실만으로 해결됐다고 말하지 않습니다.
- 회귀 테스트의 결함 탐지 능력을 주장하려면 수정 전 실패와 수정 후 성공을 확인합니다. 필요하면 격리된 환경을 쓰고, 사용자의 변경을 되돌리지 않습니다.
- 요구사항 충족은 요청한 동작과 결과물을 직접 대조합니다. 테스트 통과만으로 모든 요구사항이 충족됐다고 단정하지 않습니다.
- 다른 에이전트가 작업했다면 결과물이나 diff와 관련 검증을 확인합니다. 성공 보고만 믿지 않으며, 이 지침 자체는 에이전트 사용을 요구하거나 승인하지 않습니다.

## 검증의 최신성과 비용

- 마지막 관련 변경 이후 실행한 검증은 상태가 달라지지 않았다면 다시 사용할 수 있습니다. 새 메시지나 완료 표현을 위해 같은 검사를 반복하지 않습니다.
- 새 변경, 실패 또는 해결되지 않은 우려가 있으면 영향을 받는 검증을 다시 실행합니다.
- 승인이나 외부 접근이 필요한 검증은 기존 권한 범위를 따릅니다. 검증을 이유로 배포, 전송, 커밋이나 PR 생성까지 임의로 진행하지 않습니다.

## 로그와 최종 응답

- 긴 검증 출력은 임시 로그에 보존합니다. 성공하면 검증의 목적과 성공 여부를 짧게 보고하고, 실패하면 유의미한 오류와 원인 파악에 필요한 주변 로그만 확인합니다.
- 종료 코드나 요약만으로 결과가 불분명하면 로그 범위를 넓혀 확인합니다. 출력 축약을 이유로 실패를 숨기지 않습니다.
- 최종 응답에는 변경 결과, 실행한 주요 검증과 성공 또는 실패, 남은 문제가 있다면 그 내용을 씁니다. 검증하지 않은 결과를 추측으로 채우지 않습니다.
